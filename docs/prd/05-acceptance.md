# 自动化验收：功能与技术方案

## 1. 功能描述

用户在编码任务完成后，发起一次验收。AI 根据需求生成测试用例，用户确认后，系统准备环境、运行项目并实际检查，提供结果和证据，由用户决定是否通过。

| 功能 | 用户体验 |
| --- | --- |
| 发起验收 | 从会话或项目进入，自动整理需求，允许补充；默认检查当前已保存代码，包括未提交修改 |
| 确认用例 | 查看操作步骤与预期结果，通过编辑或对话调整，确认后开始执行 |
| 准备环境 | 自动识别依赖和启动方式，展示进度；缺权限或配置时引导处理，失败可重试 |
| 执行与接管 | 查看逐项进度和应用画面，必要时人工接管，完成后交还 AI |
| 查看结论 | 查看各项结果和截图、录像、日志；AI 提建议，用户最终确认，也可暂不判定 |
| 修复复验 | 把失败步骤及证据带回编码会话，修复后重新验收并关联原记录 |

关键规则：验收期间代码变化不影响本次被测版本；未执行、阻塞或无证据的项目不能算通过；人工接管时暂停 AI 操作；验收通过不自动合并或部署。

## 2. 技术方案

以下为结合现有 Flutter 客户端、Rust Bridge、Docker 和 x11box 代码整理的建议方案，用于评估技术取舍，不表示所有能力均已满足。

### 整体架构

```text
Flutter 客户端：确认需求与用例、审批、查看进度、接管、确认结论
       ↕
Rust Bridge：保存验收记录、编排任务、校验权限、管理控制权与证据
       ├─ 验收 Agent：提炼需求、生成计划、执行检查、分析证据
       └─ Docker 测试环境：源码快照 + 项目依赖 + x11box 桌面与浏览器
```

客户端不承担执行，退出页面不终止任务。Bridge 管理流程，Agent 负责理解与判断；权限、版本校验和资源回收由程序控制。

### 关键实现与取舍

| 环节 | 建议方案 | 适用性与代价 |
| --- | --- | --- |
| 被测代码 | 将当前工作区冻结为源码归档，记录内容哈希及排除项，复制到测试容器；可另选 Git 提交 | 支持未提交修改，也避免执行中代码变化；需要处理新文件、删除、秘密排除和采集一致性 |
| 需求与计划 | 从关联会话提炼需求，输出结构化用例；保存计划版本，确认绑定快照与计划版本 | 方便用户审阅和调整；需求提炼可能遗漏，执行前应允许用户修正 |
| 环境准备 | 以 x11box 基础镜像为底座，Agent 识别项目依赖并生成构建、启动方案；支持自定义镜像或 Dockerfile | 适合可容器化项目；首次构建慢，复杂多服务项目需要额外配置 |
| 环境复用 | 按依赖及构建配置复用镜像缓存，每次验收使用独立运行容器和测试数据 | 减少重复安装，避免旧进程及数据污染；不能仅凭项目 ID 复用环境 |
| 自动操作 | 浏览器项目优先评估 Playwright 的元素定位与断言，x11box 保留画面查看、人工接管及桌面交互 | 浏览器断言较易重复验证；混合使用时需共享同一浏览器会话。纯截图坐标操作实现统一，但稳定性较弱 |
| 人工接管 | 客户端通过 Bridge 代理访问桌面，使用短时票据和单一控制租约；确认自动操作暂停后交出控制权 | 可复用现有桌面网关；必须处理断线、旧连接和自动操作尚未停止的竞态 |
| 证据与结论 | 每项保存工具结果及对应截图、日志，录像辅助回看；AI 分析后给建议，人工结论单独保存 | 能追溯判断依据；录像占空间，截图或录像本身不一定足以证明预期满足 |
| 记录与恢复 | Bridge 持久化运行、快照、计划、逐项结果及证据索引；写操作校验版本并防重复 | 适合现有单机 Bridge；重启后先核实容器和执行者，不能直接重放可能有副作用的操作 |
| 缺陷回流 | 生成含预期、实际结果、步骤及证据的问题摘要；修复后新建快照和运行，关联原记录 | 复用编码会话，不引入独立缺陷系统；局部复验需明确结论范围 |

### 安全与资源边界

- 容器不默认挂载宿主机秘密、Docker socket 或生产数据；依赖安装脚本同样属于待执行代码，需限制权限与网络。
- 计划确认不代替权限审批。外部写入、费用及敏感操作沿用现有授权策略。
- 桌面和证据访问经过 Bridge 鉴权；结束后释放容器，证据按用户可见的保留规则清理。
- 模型调用、操作重试和运行时长设上限；无法检查时说明原因，不通过无限重试或修改预期获得成功。

## 3. 方案评估

**建议采用 Bridge 编排、容器执行、用户确认的整体架构，首批聚焦 Web 项目。** 它与现有工程结构一致，能够复用 Agent、审批、环境和桌面能力。主要需要验证的是源码一致性和自动操作可靠性，而不是先扩大支持范围。

| 关键问题 | 评估结论 |
| --- | --- |
| 是否可以直接在开发目录验收？ | 不建议默认使用。依赖安装、测试数据和自动操作容易影响开发；使用独立快照及环境更合适 |
| 是否全部通过 x11box 截图和坐标操作？ | 适合桌面接管与通用交互，但作为 Web 验收的唯一执行方式风险较高，建议对比验证 Playwright 路径 |
| 是否让 AI 自由完成全部流程？ | 不建议。AI 负责计划、操作选择和分析，Bridge 强制控制确认、权限、版本、重试及清理 |
| 是否可以用现有源码采集方式？ | 需调整：当前 Git 项目采集逻辑使用提交归档，不能覆盖默认验收未提交修改的需求，应改为工作区快照或让用户明确选择提交版本 |
| 是否马上支持任意项目？ | 不建议。先选真实 Web 项目验证完整流程，再扩展多服务及桌面项目 |

### 最小技术验证

正式扩展前，用一个有未提交修改的 Web 项目跑通以下验证：

1. 快照包含新增、修改及删除，后续编辑不会改变本次被测内容。
2. 从需求生成并确认用例，准备环境，启动的确实是该快照对应应用。
3. 对同一组正常与故障用例，对比 x11box 和 Playwright 的误判、重复执行稳定性、耗时及接管兼容性，再确定主要执行方式。
4. 人工接管期间没有自动输入；断线、重复请求和 Bridge 重启不会重复执行或产生双重控制。
5. 从失败项打开有效证据，将问题带回会话，修复后使用新快照完成关联复验。

需要共同确定的主要取舍是：首批支持哪些 Web 项目、是否引入 Playwright，以及环境自动配置允许覆盖多大的范围。
