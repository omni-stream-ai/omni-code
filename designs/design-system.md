# Omni Code 移动端设计规范 v1.0（历史提案，已暂停）

> 2026-11-03：用户已决定先记录当前应用，不采用新设计。本文件不再作为现行设计依据。现状依据见 [当前应用说明](current/README.md)。

桌面端使用 [桌面端设计规范](desktop-design-system.md) 补充布局、密度与键盘交互；本文的移动尺寸不直接套用到桌面。

制定日期：2026-11-03。规范方向：**克制、精密、有温度的开发工作台**。

本规范用于后续设计和实现。现有 `main.op`、预览和 Flutter 界面尚未完成逐项对齐；下文的尺寸与状态规则是设计目标，不能据此宣称已经落地。优先验证工作台和会话，再推广到项目、设置及全部状态稿。

## 1. 产品定位与设计原则

面向通过手机查看开发进度、发出任务、处理审批与检查结果的用户。界面应让人随时回答：当前在哪个项目、任务进行到哪里、下一步能做什么。

| 原则 | 设计要求 | 避免 |
|---|---|---|
| 内容优先 | 正文、执行结果与审批信息占据主要空间 | 装饰挤占正文和操作位置 |
| 层级明确 | 通过字号、间距、表面和对齐建立主次 | 所有信息都套同样的卡片 |
| 状态可信 | 区分处理中、等待确认、成功与失败 | 请求发出后立即显示成功 |
| 操作可控 | 影响范围、可用动作和操作反馈清楚可见 | 只靠图标或颜色表达关键操作 |
| 视觉克制 | 石墨与暖白承载内容，青柠集中表达主操作 | 大面积强调色、连续渐变和重阴影 |

品牌 Logo 保留原有比例与渐变；品牌渐变不自动扩展为页面背景风格。

## 2. 信息与页面结构

同一任务区域只设置一个主要操作。同屏可以有多个独立任务区域，但须形成清晰主次；审批区域可同时呈现批准与拒绝，拒绝使用危险样式。

| 优先级 | 内容 | 表现 |
|---|---|---|
| 需立即处理 | 阻塞审批、失败、连接中断 | 靠近关联任务，使用状态图标、文字与局部色彩 |
| 当前任务 | 执行阶段、最近输出、可执行主操作 | 主内容区，标题与正文明确 |
| 上下文 | 项目、模型、时间、分支 | 辅助文字，必要时可展开 |
| 辅助入口 | 设置、历史与次要操作 | 次按钮、列表行或更多菜单 |

工作台：页面标题 → 紧凑状态摘要 → 待处理审批（存在时）→ 最近会话 → 最近项目。统计只表示当前已加载范围，并提供必要说明。欢迎信息不应比任务本身更抢眼。

会话：项目与会话上下文 → 执行状态 → 连续消息 → 输入区。状态区可收起详细过程，但保留当前阶段与阻塞原因；输入区和审批操作不得遮挡最后一条消息。

项目：项目身份与必要信息 → 主要入口 → 会话列表。设置：按账户、模型、语音、扩展等任务分组；一个列表行只承载一个主要动作。

## 3. 基础颜色与主题

颜色数值以 [tokens.json](tokens.json) 为准。以下列出当前已存在的语义角色；后续页面通过角色引用，不自行增加近似色。深浅主题保持相同的信息层级，不做简单反色。

| Token | 深色 | 浅色 | 用途 |
|---|---|---|---|
| `bg` | `#121617` | `#F7F8F5` | 页面背景 |
| `panel` | `#222A2B` | `#FFFFFF` | 卡片、输入等主要表面 |
| `panel-soft` | `#1A2122` | `#FFFFFF` | 次级分组表面 |
| `text` | `#F0F4EF` | `#202A29` | 标题、正文 |
| `secondary` | `#C0CCC7` | `#485A55` | 次级说明 |
| `muted` | `#9BAEA6` | `#63766C` | 时间、元信息、占位提示 |
| `line` | `#34413D` | `#DBE3DC` | 装饰分隔、低强调边框 |
| `accent` | `#C7F18B` | `#C6EB91` | 主按钮与局部强调背景 |
| `accent-ink` | `#20311C` | `#24391C` | 强调背景上的文字与图标 |
| `green` / `green-bg` | 见变量文件 | 见变量文件 | 成功与完成 |
| `amber` / `amber-bg` | 见变量文件 | 见变量文件 | 审批、等待处理与警告 |
| `link` | `#C0E89A` | `#446B32` | 正文链接，配合下划线 |

青柠不能作为浅色背景上的小字号文字颜色。选中态结合图标、字重或形状提示；完成状态需要“已完成”等文字，避免与主操作混淆。运行中用进度或阶段描述表达，不能只用绿色圆点。

代码使用 `code`、`code-keyword`、`code-string`；引用使用 `quote-bg`；Diff 使用 `code-add*` 与 `code-del*` 并保留 `+` / `−` 标识。这些内容色不得承担应用错误提示的角色。

**新增角色，待组件验证后写入变量文件：**

| 角色 | 深色 | 浅色 | 用途 |
|---|---|---|---|
| `danger` | `#FFB4AB` | `#B42318` | 错误、危险操作文字与图标 |
| `danger-bg` | `#392321` | `#FFF0EE` | 局部错误提示背景 |
| `focus-ring` | `#C7F18B` | `#446B32` | 键盘焦点外框 |

普通正文和必要辅助文字对比度至少 4.5:1；大号文字至少 3:1；关键图标、焦点和用于识别控件的边界至少 3:1。`line` 仅用于装饰分隔，不能单独承担控件识别。输入框需靠表面与边界共同建立识别，不足时增加可达到 3:1 的边界角色。每次调整需检查实际前景与背景组合。

## 4. 字体与排版

Latin 使用 Roboto，中文预览使用 Noto Sans CJK SC，代码预览使用 DejaVu Sans Mono。Flutter 中文回退字体尚未固定，实施时检查目标设备字形和换行；不能把预览字体视为已随应用分发。

| 样式 | 字号 / 行高 | 字重 | 场景 |
|---|---|---|---|
| 页面标题 | 28 / 36 | 700 | 工作台、项目、设置标题 |
| 紧凑页标题 | 20 / 28 | 600 | 会话顶部、弹层标题 |
| 分区标题 | 18 / 26 | 600 | 最近会话、审批分区 |
| 条目标题 | 16 / 24 | 600 | 会话与项目名称 |
| 正文 | 16 / 26 | 400 | 消息、说明与表单内容 |
| 操作标签 | 14 / 20 | 600 | 按钮、标签页 |
| 辅助信息 | 13 / 20 | 400 | 时间、模型、路径说明 |
| 极短标记 | 12 / 16 | 500 | 数量徽标，不承载长句 |
| 代码 | 13 / 20 | 400 | 命令、日志与 Diff |

数值是逻辑像素，字体随系统文字缩放。中文字符间距为 0；不用负字距制造紧凑感。正文左对齐，长标题允许换行；列表摘要可截断并通过详情访问全文。审批命令、错误原因与关键风险描述不得只显示省略文本。文件路径可视觉截断，但支持查看或复制完整值。

## 5. 布局、间距与表面

以 4 为基本步长，采用 4、8、12、16、20、24、32、40。图标与文字间距 8；标题与说明 8；组内元素 12；卡片内边距 16；页面边距 20；区块间距 24，重大分区可用 32。避免无语义的任意数值。

设计基准为 390 × 844，检查 320、390、430 宽度和系统文字放大至 200% 的布局。窄屏先换行、堆叠和滚动；不能靠缩小字号或操作热区适配。内容高度由内容决定，预览固定高度不等于实现固定高度。宽屏布局另行验证，保留现有路由与能力边界。

| 项目 | 规则 |
|---|---|
| 圆角 | 控件 12、卡片 16；标签与选中导航可胶囊化；底部弹层顶部 24 |
| 边框 | 普通 1；焦点框 2，向外偏移 2，不改变布局 |
| 阴影 | 普通列表不使用；浅色浮层可用 `0 4 16 rgba(0,0,0,.08)` |
| 深色层级 | 优先表面明度与边界，避免靠黑色阴影区分 |
| 渐变 | 默认不用；仅在核心页面验证有明确收益时局部使用 |
| 安全区 | 顶部、导航底部和输入区均考虑系统安全区与键盘 |

卡片用于独立任务、审批和可操作摘要。连续消息、普通设置列表不逐行套卡片；避免卡片内再叠同样的卡片。除弹层遮罩外，页面视觉表面通常不超过三级。

## 6. 组件规则

| 组件 | 结构与尺寸 | 行为与变体 |
|---|---|---|
| 主按钮 | 高度至少 48，水平内边距 16，文字与图标间距 8 | `accent` + `accent-ink`；用于当前区域主要动作 |
| 次按钮 | 高度至少 48，表面或边框样式 | 承担查看、取消等次要动作 |
| 危险按钮 | 同等热区，危险色与明确动词 | 如“拒绝”“删除”；不可仅靠红色区分 |
| 图标操作 | 20 图标置于至少 44 × 44 热区 | 必须有无障碍名称；密集操作间留 8 |
| 输入框 | 单行至少 48，内边距 12–16，常驻标签 | 占位符仅作示例；错误贴近字段并保留输入 |
| 会话输入 | 多行自适应，正文 16，操作不覆盖输入 | 草稿与排队消息规则依当前功能；键盘弹出后仍可发送 |
| 列表行 | 单行至少 56；双行至少 72，内边距 16 | 主标题、摘要、元信息分层；右侧操作有独立热区 |
| 卡片 | 内边距 16，组内间距 12，圆角 16 | 可点击卡片需有明确入口；内部独立按钮不重复触发卡片 |
| 状态标签 | 字号 12–13，水平内边距 8，垂直 4 | 状态文字为必需，图标辅助；可点击时热区至少 44 |
| 底部导航 | 图标 20，文字 12，内容区至少 64，加底部安全区 | 工作台、项目、设置；选中项有局部背景及文字提示 |
| 顶部栏 | 内容区至少 56，加顶部安全区 | 返回、标题、必要动作；长标题不得挤掉操作 |
| 底部弹层 | 内边距 20，顶部圆角 24 | 标题、内容、操作；长内容滚动，主要动作与键盘避让 |
| 搜索 | 高度至少 48 | 清空与取消可识别；保留查询条件并区分无结果与未搜索 |

所有高度是最小值；文字放大时允许增长。按钮的默认、按下、焦点、禁用、提交中、失败状态都需设计。按下采用局部表面变化，禁用同时表达不可用原因（有必要时）；禁止通过降低整个容器透明度使说明不可读。提交中维持按钮宽度、显示进度与动作文字，并防止重复提交。

### 审批面板

顺序为：请求类型 → 具体命令或影响内容 → 范围与风险说明 → 可用操作 → 提交反馈。琥珀色只强调请求身份与阻塞状态，不给整屏染色。命令可展开和复制；批准、拒绝及其他选项仅按当前请求能力出现。保留提交中、等待执行端确认、失败、已解决状态；请求发出不能直接变成“已批准”。

### 消息与工具结果

用户与助手通过角色、位置和局部表面区别，连续正文保持稳定阅读宽度。工具调用默认显示名称、状态与摘要，详情展开；错误不折叠到无法察觉。代码保持原始缩进并支持横向滚动与复制；表格独立横向滚动，不带动整页。图片约束宽度且保留比例；视频有显式播放入口和加载失败反馈。链接、文件、Diff 按 [内容规范](content.md) 及当前解析能力设计，不能把未支持的内容表现为可用功能。

## 7. 状态、反馈与动效

| 状态 | 展示 | 可用动作 |
|---|---|---|
| 首次加载 | 局部骨架或进度及明确对象 | 可取消时提供取消；避免空白屏 |
| 后台刷新 | 保留已有内容，局部提示 | 保持可用操作，按实际条件禁用冲突动作 |
| 空数据 | 说明这里将出现什么 | 有权限和能力时给创建入口 |
| 无搜索结果 | 展示查询语义与无匹配说明 | 清空筛选或修改查询 |
| 执行中 | 当前阶段、近期输出和进度 | 按能力提供停止等操作，不伪造百分比 |
| 等待审批 | 明确阻塞原因与请求内容 | 按请求能力显示操作 |
| 断开连接 | 提示当前连接情况与数据可能过时 | 重连；明确发送是否可排队 |
| 失败 | 说明失败对象、原因与恢复路径 | 重试、编辑或查看详情；保留草稿 |
| 完成 | 明确最终结果及相关证据 | 查看变更、验证结果或下一步 |

本地消息 queued、pending、submitted、failed 的动作按 [现有状态表](states.md) 保留，不由视觉规则重新定义业务。重要失败使用持续可见的局部提示；短暂浮动提示只用于复制成功等不要求后续操作的反馈。提交结果在关联位置更新，读屏可感知状态变化。

状态变化以 120–200ms 的颜色或透明度过渡为主，弹层进入可用 200–240ms。遵循减少动态效果设置，关闭位移与循环装饰动画；处理过程仍通过文字和进度标识表达。新消息不强制把正在阅读历史的用户拉到底部，提供新消息入口。

## 8. 可用性与文案

操作使用明确动词，如“新建会话”“重试发送”“查看变更”。错误描述包含对象和恢复方法；避免只写“失败”或暴露没有帮助的实现术语。状态与可用能力一致，不能用视觉暗示尚未存在的操作。

关键操作不只依赖手势、悬停或颜色。键盘可到达所有可操作元素，焦点顺序与视觉顺序一致，关闭弹层后返回触发处；弹层有明确关闭方式。图标按钮有可读名称；状态变化有辅助技术提示。正文可选择，路径与命令可复制，媒体有必要的替代说明。至少支持 44 × 44 操作热区，并为文字放大与换行保留空间。

## 9. 资产与设计源维护

规范入口为本文件；颜色数值来源为 `tokens.json`；可编辑画稿为 `main.op`；功能条件以 Flutter 源码为准，设计映射在 `coverage.json` 和 `states.json`。规范描述预期，画稿与实现是否符合需由验收记录确认。

复用 `assets/logo.svg` 与 `assets/icons/`。图标源为 24 × 24、2px 描边，默认显示 20 × 20；不混用 Emoji 或不同粗细的图标。中文不用拉丁字体强制替代。

通用颜色变量与 `dark-*` / `light-*` 同步维护。新增角色先列出用途、主题值和对比度验证，再进入变量文件与组件；不为单个页面建立近似色。非颜色尺寸暂以本规范为准，已有 `radius-card`、`radius-control`、`space-page` 继续复用，后续按组件验证结果补齐 token。OpenPencil 维护步骤见 [README](README.md#使用-openpencil-cli-维护)。设计变量不会自动修改 Flutter。

## 10. 落地顺序与验收

1. 建立深浅组件样板：按钮全状态、输入错误与焦点、列表、导航、审批、执行状态和消息输入。
2. 验证工作台与会话：正常、空态、加载、失败、等待审批、长内容；同时检查两种主题与窄屏、大字号。
3. 根据样板修正规范并同步变量，然后推广到项目、设置和所有状态稿。
4. 更新设计源、预览、状态映射与验收记录；Flutter 实施另行验证设备上的布局和交互。

每批验收均记录页面或组件、主题、宽度、文字缩放、状态、问题与结论。至少满足：

- 关键入口和业务条件保留，提交与确认状态准确。
- 主次清楚，颜色与尺寸可追溯到本规范及 token。
- 正文和控件对比度满足要求，焦点与错误可识别。
- 320 宽及 200% 文字下无文字覆盖、操作遮挡或关键内容截断；代码与表格可独立滚动。
- 键盘、安全区、长标题、长路径、多条审批和长消息均有处理。
- 设计源与导出预览一致；功能与状态记录的节点引用保持有效。

当前完成：设计原则、基础样式、组件与交互规则的文档定义。待完成：组件样板验证、两张核心页面验证、变量扩展、全量画稿对齐与应用实施。本次规范制定不代表这些验证已通过。
